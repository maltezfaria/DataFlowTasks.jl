DataFlowTasks.DAG — Type
struct DAG{T}

Representation of a directed acyclic graph containing nodes of type T. The list of nodes with edges coming into a node i can be retrieved using inneighbors(dag,i); similarly, the list of nodes with edges leaving from i can be retrieved using outneighbors(dag,i).

DAG is a buffered structure with a buffer of size sz_max: calling addnode! on it will block if the DAG has more than sz_max elements.

The DAG is thread-safe: mutating operations acquire dag.lock, and the conditions cond_push and cond_empty are associated with that same lock.

DataFlowTasks.DataFlowTask — Type
DataFlowTask(func,data,mode)

Create a task-like object similar to Task(func) which accesses data with AccessMode mode.

When a DataFlowTask is created, the elements in its data field will be checked against all other active DataFlowTask to determined if a dependency is present based on a data-flow analysis. The resulting Task will then wait on those dependencies.

A DataFlowTask behaves much like a Julia Task: you can call wait(t), schedule(t) and fetch(t) on it.

See also: @dtask, @dspawn.

DataFlowTasks.LogInfo — Type
mutable struct LogInfo

Contains informations on the program's progress. Events are appended to the logs under lock, so that a LogInfo can be safely shared by all threads.

Besides the logs of the tasks and of their insertion, a LogInfo records the logging window (time_start and time_finish, in nanoseconds), the number of threads available to run the tasks (nworkers), and the time spent in garbage collection and compilation during the window (gc_time and compile_time, in seconds).

Use DataFlowTasks.describe or DataFlowTasks.summarize to analyze a LogInfo, and GraphViz.Graph or Makie.plot to visualize it.

Note

A LogInfo keeps references to the data accessed by the logged tasks until their dependencies are first needed (e.g. by describe), so that the complete dependency graph of the tasks can be computed.

DataFlowTasks.LogSummary — Type
struct LogSummary

Summary of the events recorded in a LogInfo, as computed by DataFlowTasks.summarize. All times are in seconds.

Fields:

  • elapsed : wall-clock time of the logging window
  • workers : number of threads available to run the tasks (the threads of the :default threadpool)
  • running : total time the tasks spent running
  • blocked : total time the tasks spent descheduled during their body (sleeping, waiting on I/O or on a lock...)
  • insertion : total time spent inserting the tasks in the DAG (on the threads calling @dspawn)
  • critical_path : length (in wall time) of the longest chain of dependent tasks
  • gc, compile : time spent in garbage collection and in compilation during the logging window
  • categories, running_per_category : the categories of tasks, and the running time of the tasks in each of them (the last entry gathers the tasks matching no category)
  • path : tags of the tasks on the critical path
  • ntasks, nfailed, nmigrated : number of tasks, of tasks which threw an error, and of tasks which finished on another thread than the one they started on

The following quantities are derived from these fields:

  • capacity(s) = s.workers * s.elapsed: the time the workers were available;
  • idle(s) = capacity(s) - s.running: the time the workers did not run any task;
  • nowait(s) = s.running / s.workers: the elapsed time if the running time were perfectly shared between the workers, without ever waiting.

Both critical_path and nowait are lower bounds of elapsed.

DataFlowTasks.TaskGraph — Type
struct TaskGraph

A directed acyclic graph used to reprenset the dependencies between DataFlowTasks.

TaskGraph(sz) creates a task graph that can hold at most sz elements at any given time. In particular, trying to add a new DataFlowTask will block if the TaskGraph is already full.

See also: get_active_taskgraph, set_active_taskgraph!

DataFlowTasks.TaskLog — Type
struct TaskLog

Logs the execution trace of a DataFlowTask.

Fields:

  • tag : task id in DAG
  • time_start : time the task body started running (after waiting for its dependencies)
  • time_finish : time the task body finished running
  • running_time : time the task body spent actually running on a thread, i.e. excluding the time it was descheduled (sleeping, waiting on I/O or locks...)
  • tid : thread on which the task body started
  • tid_finish : thread on which the task body finished (a task may migrate between threads when it is descheduled)
  • inneighbors : vector of incoming neighbors in DAG
  • label : a string used for displaying and/or postprocessing tasks
  • failed : whether the task threw an error

All times are in nanoseconds.

DataFlowTasks.memory_overlap — Method
memory_overlap(di::AbstractArray,dj::AbstractArray)

Try to determine if the arrays di and dj have overlapping memory.

When both di and dj are Arrays of bitstype, simply compare their addresses. Otherwise, compare their parents by default.

When both di and dj are SubArrays we compare the actual indices of the SubArrays when their parents are the same (to avoid too many false positives).

DataFlowTasks.@dspawn — Macro
@dspawn expr [kwargs...]

Spawn a Julia Task to execute the code given by expr, and schedule it to run on any available thread.

Annotate the code in expr with @R, @W and/or @RW to indicate how it accesses data (see examples below). This information is used to automatically infer task dependencies.

Additionally, the following keyword arguments can be provided:

  • label: provide a label to identify the task. This is useful when logging scheduling information;
  • priority: an integer in 0:65535 (0 by default) setting the priority of the underlying Julia Task. As in Julia, 0 is the most urgent: when several tasks are waiting for a thread, the ones with a smaller priority value tend to be started first. Priorities do not interrupt running tasks, are only approximately respected, and have no effect when the :default threadpool has a single thread.

Semantics

  • The task is inserted in the active TaskGraph (see get_active_taskgraph) before @dspawn returns. Its dependencies are inferred from the tasks already in the TaskGraph, so that they follow the order of the @dspawn calls (see nested tasks for the case of tasks spawned concurrently).
  • If the TaskGraph is full, @dspawn blocks until a task finishes (see resize!).
  • The task runs on the :default threadpool, once all the tasks it depends on have finished. If one of them failed, the task fails as well.
  • @dspawn returns the Julia Task running the DataFlowTask, which can be waited on or fetched.

Examples:

Below are 3 equivalent ways to create the same Task, which expresses a Read-Write dependency on C and Read dependencies on A and B

using LinearAlgebra
using DataFlowTasks
A = ones(5, 5)
B = ones(5, 5)
C = zeros(5, 5)
α, β = (1, 0)

# Option 1: annotate arguments in a function call
@dspawn mul!(@RW(C), @R(A), @R(B), α, β)

# Option 2: specify data access modes in the code block
@dspawn begin
   @RW C
   @R  A B
   mul!(C, A, B, α, β)
end

# Option 3: specify data access modes after the code block
# (i.e. alongside keyword arguments)
res = @dspawn mul!(C, A, B, α, β) @RW(C) @R(A,B)

fetch(res) # a 5×5 matrix of 5.0

Here is a more complete example, demonstrating a full computation involving 2 different tasks.

using DataFlowTasks

A = rand(5)

# create a task with WRITE access mode to A
# and label "writer"
t1 = @dspawn begin
    @W A
    sleep(1)
    fill!(A,0)
    println("finished writing")
end  label="writer"

# create a task with READ access mode to A
t2 = @dspawn begin
    @R A
    println("I automatically wait for `t1` to finish")
    sum(A)
end  priority=1

fetch(t2) # 0

# output

finished writing
I automatically wait for `t1` to finish
0.0

Note that in the example above t2 waited for t1 because it read a data field that t1 accessed in a writable manner.

DataFlowTasks.@log — Macro
DataFlowTasks.@log expr --> LogInfo

Execute expr and return a LogInfo instance with the recorded events. The DataFlowTasks created by expr (directly, or by the tasks it creates) are logged, and @log waits for them to be completed before returning.

Tasks which are not logged (e.g. spawned before @log, or by other code running concurrently) may still run during the logging window: the time the workers spend on them is reported as idle. For clean measurements, wait for such tasks before logging, e.g. with wait(get_active_taskgraph()).

See also: with_logging, with_logging!

Makie.plot — Method
plot(log_info; categories)

Plot DataFlowTasks log_info labeled informations with categories.

Entries in categories define how to group tasks in categories for plotting. Each entry can be:

  • a String: in this case, all tasks having labels in which the string occurs are grouped together. The string is also used as a label for the category itself.
  • a String => Regex pair: in this case, all tasks having labels matching the regex are grouped together. The string is used as a label for the category itself.
